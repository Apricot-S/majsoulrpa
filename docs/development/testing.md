# テストと品質基準

## TDD 手順

MajsoulRPA の実装は t_wada の TDD に従います。

1. テストリストを作る
2. ひとつテストを書く
3. テストを成功させる
4. テストが通る状態を保ったまま、実装とテストをリファクタリングする
5. テストリストの構造をテストコードへ反映する
6. 開発途中だけ必要だったテストを整理する

テストリストは、実装前に作ります。実装中に見つかったケースは、
都度テストリストへ追加します。

リファクタリングはプロダクトコードだけを対象としません。テストも、後から
参加した開発者が実行結果から仕様を読み取れる「動作する仕様書」にします。

## テストの構造化

テストリストで同じ対象や状況に属する項目は、テストコードでも同じまとまりに
します。pytest では、directory / module を機能領域、`test_...` function を
観測可能な振る舞いとする階層を基本とします。

1 module が 1 つの対象や状況だけを表す場合は、module-level test function の
ままにします。ファイル名と同じ意味の `Test...` class を 1 つだけ追加しても、
仕様の情報量は増えません。`self`、indent、node ID 変更だけを増やす構造化は
行いません。

1 module に意味の異なる対象や状況が複数ある場合は、それらを表す `Test...`
class を追加してよいものとします。class 名と method 名を組み合わせたときに、
前提と期待する振る舞いが分かる名前にします。fixture や setup の共通化だけを
目的に class を導入せず、共有 mutable state や `__init__` も持たせません。

fake、builder、共通データは module level に置き、複数 module で意味のある
再利用がある場合だけ `_support.py` や `fakes.py` へ移します。パラメータ値だけ
では仕様の違いが読めない場合は、意味を表す parameter ID を付けます。

## 不要になったテストの整理

仮実装から一般化するための三角測量など、開発途中のフィードバックだけを目的に
追加したテストは、役目を終えた時点で書いた人が整理します。

同じ仕様、同じ失敗理由、同じ観測点を持ち、任意の入力値だけが異なるケースは、
代表する 1 ケースへ統合または削除します。一方、次のケースは重複に見えても
維持します。

- 境界値または異なる同値 class を表す
- 正常系と異常系、または異なる validation failure を表す
- timeout、cancellation、cleanup など異なる失敗経路を表す
- protocol variant、player count などで規則が異なる
- 別の不具合に対する regression test である

削除件数は目標にしません。なぜ不要になったか、どの残存テストが同じ仕様を
代表するかを説明できないテストは残します。private 実装を直接確認していること
だけを削除理由にはせず、守る契約と失敗経路から判断します。

## テストリストの置き場所

実装が始まったら、テストリストの置き場所を決めます。

候補:

- `docs/development/test-plan.md`
- issue / task tracker
- 対象モジュール近くの design note

どれを選ぶ場合も、テストリストが実装より先に存在する状態を守ります。

## 自動テストで禁止するもの

自動テストでは以下を使いません。

- 実際の雀魂へのアクセス
- 実 AWS
- 実メール
- 実認証コード
- 実 Cookie
- 実アクセストークン
- ライブ通信キャプチャ
- 実アカウントが写ったスクリーンショット

外部依存が必要な挙動は、fake、stub、synthetic data で表現します。

## テストの種類

優先するテスト:

- config の default と validation
- callback dispatch
- Presentation 検出の優先順位
- timeout と cancellation
- lifecycle の開始、停止、異常終了
- capture hook の dispatch
- secret が repr/log/exception に出ないこと

実ブラウザが必要なテストは、自動テストではなく手動確認として扱います。

## 品質ゲート

基本コマンド:

```sh
python -m pytest
python -m ruff check .
python -m ruff format --check .
python -m ty check
```

変更範囲が狭い場合は、まず関連テストだけを実行してよいです。ただし、
共有基盤、config、runtime、Presentation、capture に触れた場合は、
最終確認で全体の品質ゲートを通します。

## 例外と fallback

禁止:

- 広い例外捕捉で処理を続ける
- 失敗した操作を成功として扱う
- decode 失敗を空 message として扱う
- timeout を通常完了として扱う
- cleanup 失敗を完全に無視する

許容:

- cleanup 中の副次的な失敗を主例外に添えて報告する
- retry 条件が明確な一時失敗だけ retry する
- ユーザーが明示的に選んだ degraded mode

## 手動確認

高レベル API を 1 つ実装するごとに、ユーザーへ実際の雀魂での確認を依頼します。

確認依頼には以下を含めます。

- 確認対象 API
- 実行手順
- 期待する画面遷移
- ログや保存物に秘密情報が出ないこと
- 実通信や画像を保存する場合の削除方針

ユーザー確認が終わるまで、次の高レベル API 実装へ進みません。
