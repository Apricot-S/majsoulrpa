# 加槓候補の牌順序

## 調査目的

`OptionalOperation.type == 6` の `combination` から、既存のポンと加える牌をどのように
区別できるかを確認する。

## 観測結果

実牌譜に含まれる赤5絡みの加槓を調査したところ、`combination` の赤5は、既存のポンに
含まれる牌か加える牌かにかかわらず、調査対象の全例で先頭に置かれていた。赤5が末尾に
置かれた例は確認されていない。このため、たとえば `0s|5s|5s|5s` という同一の文字列が、
次のどちらも表し得る。

- 通常の5索3枚のポンへ赤5索を加える
- 赤5索を含むポンへ通常の5索を加える

この観測から、加槓候補の `combination` は副露時の牌順を保持せず、少なくとも赤5を先頭へ
置く正規化が行われていると判断する。末尾を加える牌として扱うことはできない。

一方、牌譜の `RecordAnGangAddGang` の `type == 2` では、`tiles` に加えた牌1枚だけが
格納される。ライブ対局では対応するメッセージ名が `ActionAnGangAddGang` となる。成立後の
Event では、この `ActionAnGangAddGang.tiles` から追加牌を直接かつ一意に取得できる。

## 設計への反映

- `JiagangOperation` の候補生成時は `combination` の位置に意味を持たせない。
- 現在の `RoundState` にある既存の `Peng` と4枚の multiset を比較し、差分の1枚を
  `added` とする。これにより赤5と通常の5を区別する。
- 加槓成立後の Event は、ライブ対局の `ActionAnGangAddGang.tiles` を追加牌として扱う。
- チーとポンでは `RecordChiPengGang.tiles` と `froms` が副露時の牌順を保持するため、
  取得牌を末尾から取り出す現在の規則を維持する。
- 暗槓は4枚すべてが自家の牌であり、取得牌との分割はない。現時点では暗槓・加槓とも、
  使った牌が手牌位置とツモ牌位置のどちらにあったかを公開状態では区別しない。
